**建议：先用进程内字典（最好用带 TTL/容量上限的，比如 Python 的 `cachetools.TTLCache` 或 `functools.lru_cache`）。**

100 人的内部工具，流量很小，Redis 带来的收益基本用不上，却会多出一个要部署、监控、维护的组件。

**进程内缓存够用的情况：**
- 只跑一个进程/实例（或者多实例但缓存不一致可以接受）
- 缓存丢了无所谓，重启后重新预热即可
- 缓存的数据量不大（几十 MB 以内）

**这些情况再上 Redis：**
- 多个 worker/实例，且需要缓存一致（比如改了数据要立刻对所有人生效）
- 需要重启后缓存还在（比如缓存的是很贵的计算结果）
- 缓存里放的是需要跨进程共享的状态，如会话、限流计数、分布式锁
- 你的部署环境里本来就有 Redis，接入成本几乎为零

**几个注意点：**
1. 注意多 worker 的坑：如果用 gunicorn/uvicorn 起了 4 个 worker，每个进程各有一份字典，命中率会下降、数据可能短暂不一致。小工具可以直接单 worker 或接受这点。
2. 一定要设 TTL 和大小上限，裸字典会无限增长。
3. 把缓存访问封装成一个小函数/类（`get_cached(key, loader)`），以后真要换 Redis 只改这一处。
